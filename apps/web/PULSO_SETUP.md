# Pulso setup and implementation status

From `apps/web`, run `npm ci`, `npm test`, and `npm run dev` (or `npm run build`). The app requires Convex and Google sign-in configuration; it does not silently fall back to sample data. There is no syllabus upload or import.

## Firebase and Convex configuration

This checkout previously used direct Google Identity Services. It now uses Firebase Authentication with Google Sign-In; it does not use Convex Auth. Firebase must be configured and tested before rollout. Create or select the intended Firebase project, enable Google under Authentication → Sign-in method, and authorize the Vercel domain and localhost in Firebase Authentication settings. Follow the Firebase/Google consent-screen and domain restrictions for your institution. Configure a Firebase Web app and set these **public config** values for the frontend (Vercel and `apps/web/.env.local` for local development):

- `NEXT_PUBLIC_CONVEX_URL` — the intended Convex deployment URL
- `NEXT_PUBLIC_FIREBASE_API_KEY`, `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN`, `NEXT_PUBLIC_FIREBASE_PROJECT_ID`, `NEXT_PUBLIC_FIREBASE_APP_ID` — from Firebase Web app settings

Firebase's web API key identifies the project and is not a server secret; protect data with Firebase/Convex authorization rather than hiding it. Do not paste credentials into chat. Set `FIREBASE_PROJECT_ID` in the **Convex deployment** to the exact same Firebase project ID, then deploy Convex functions and `auth.config.ts`. The issuer is `https://securetoken.google.com/<project-id>` and the audience is the project ID. Firebase signs ID tokens using RS256; its configured public signing-key endpoint returns a JWKS. Confirm a real token's issuer, audience and key ID match the configured Firebase project and JWKS before rollout. The application does not log or manually store ID tokens; Firebase manages its own session persistence and token refresh. A sign-out ends the local Firebase session.

For a new installation, set `PULSO_BOOTSTRAP_ADMIN_EMAIL` in Convex to the first administrator's university email. The first admin signs in and uses **Set up first administrator**. Remove this variable after bootstrap. A new university-domain identity automatically receives a student account at sign-in; it does not automatically join a section. Existing accounts still link once to their matching LSPU email, and disabled or already-linked records cannot be recreated. Admins can change existing accounts between student and instructor in Accounts. The only non-university email exceptions are `johnalexalcazar@gmail.com` and `alcazarjohnalex@gmail.com`, which automatically receive admin accounts on first sign-in. Disabled or already-linked records are not bypassed. A current deployment with existing accounts does not need a second bootstrap. **Security tradeoff:** Email verification is not checked, including during bootstrap or account linking. A Firebase identity with an unverified matching email may claim an unlinked approved account, including the bootstrap administrator; it may also register as an exception admin if it asserts an exception email. Enable only trusted Firebase sign-in providers and review account ownership before deployment; a domain suffix alone does not prove mailbox ownership. The link writes the Firebase UID to the existing record without changing its role, memberships or ownership. Thereafter access is determined by the stored UID, not by email. The administrator must verify that old approved email records still belong to their intended users before cutover; recycled or reassigned emails could otherwise be claimed by a different account. Disable questionable accounts before migration. A linked record cannot be claimed by another UID. There is no self-service reset of UID links; account recovery requires an administrator-reviewed procedure. Users whose account has been disabled cannot link or access it.

**Cutover:** Firebase and Convex auth configuration must be deployed together. Replacing the old Google issuer stops accepting old Google ID tokens; coordinate the frontend and Convex rollout and expect users to sign in again. A Firebase project change produces different UIDs and requires a separately reviewed migration. No existing course or user records are deleted by this change.

The persistent student Classroom connection uses a separate Google OAuth web client and server-side routes. Configure the following **server-only** Vercel environment variables (never prefix them with `NEXT_PUBLIC_`):

- `GOOGLE_CLASSROOM_CLIENT_ID` and `GOOGLE_CLASSROOM_CLIENT_SECRET`: the Google OAuth web client credentials.
- `CLASSROOM_REDIRECT_URI`: the exact production URL `https://YOUR-VERCEL-DOMAIN/api/classroom/callback`. Add the same URL to the OAuth client's authorized redirect URIs in Google Cloud. Use the same origin as the website; configure separate clients and keys for other environments.
- `CLASSROOM_ENCRYPTION_KEY`: a random 32-byte base64 key. Generate it locally with `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`, enter it as a sensitive Vercel variable, and never share it. Keep it stable: changing or losing the key makes existing saved connections unreadable and students must reconnect. Plan secure backup and rotation before production.

Enable Classroom API in the OAuth client's Google Cloud project. Configure the consent screen and test users, and grant the read-only courses and own coursework scopes. Google Workspace restrictions or testing-mode refresh-token expiration can require reconnecting. The student must choose the same Google account as their Firebase login; its Google subject is matched before storing credentials. The server encrypts refresh tokens with AES-256-GCM bound to Firebase UID and saves the ciphertext in Convex. Classroom content itself is fetched on request, not persisted. Disconnect deletes the saved ciphertext and attempts Google revocation; if revocation fails, the student must revoke access from Google Account settings. Sign-out alone does not delete the connection. Never put secrets, deploy keys or refresh tokens in a `NEXT_PUBLIC_` variable, Git, logs or chat. Deploy both the Convex schema/functions and the Vercel app before testing. The persistent OAuth flow has not been verified with live credentials.

If deploying Convex functions as part of Vercel builds, set private `CONVEX_DEPLOY_KEY` as a sensitive Vercel variable and use a build command such as `npx convex deploy --cmd 'npm run build'` with root directory `apps/web`. Ensure the key and `NEXT_PUBLIC_CONVEX_URL` refer to the same Convex deployment and configure `FIREBASE_PROJECT_ID` there before deployment. Alternatively deploy Convex separately. Redeploy the frontend after changing its environment variables.

## Verification and limitations

The local tests use mock Convex identities to exercise UID linking, role and section authorization; they do **not** verify JWT signatures or a live Firebase login. Before using real data, deploy to a development environment and test Google sign-in, session restoration on reload, token refresh, sign-out, disabled accounts, existing account linking, and rejection of tokens from a different project, expired tokens and invalid signatures. Verify the current JWKS and token `kid`. Live Firebase/Convex authentication has not been tested in this workspace. The AI study assistant and instructor Classroom integration are not implemented. The persistent student Classroom flow has not been tested with live Google accounts. The current screens do not implement every planned feature. Review privacy, retention and scale before production use.

## Updated academic-section model and migration

Pulso now models a fixed academic section for a specific term, with one or more subject course offerings. Administrators create academic sections, assign each student one primary section, and create course offerings for it. Every primary member receives the same recorded section deadlines and weekly score. Instructor collision checks aggregate all registered offerings in the section; they explicitly warn that unrecorded subjects or deadlines are not included. The heatmap uses section-week scores, not independent student averages. Small sections remain suppressed.

**Existing deployments require explicit administrator migration.** Existing `courses`, `memberships` and deadline records are not deleted or automatically mapped. In **Sections**, create each academic section and term, select it, then map each pre-existing unmapped offering after verifying the cohort. Assign students to their primary section after checking enrollment records. Old individual course memberships are displayed separately as personal schedule adjustments until verified; once an offering belongs to the student's primary section, it is not duplicated as an adjustment. Unmapped offerings cannot produce a shared-section collision estimate. A course mapping cannot currently be undone in the UI; verify it carefully before confirming. The migration does not automatically create new shared membership or alter existing records based on matching names.

Classroom access is read-only and has not been tested end to end; saved connections persist and data is refreshed on request. Classroom snapshots and confirmed course-wide work are handled separately from the legacy manually assigned section scores. AI study planning, verified cross-section exclusions, historical memberships and section/offering edits or deletion are not implemented. Existing individual memberships should not be assumed to be verified exceptions. Do not use the new shared schedule for real scheduling until all offerings, membership and migration data have been checked and deployment end-to-end tested.

## Troubleshooting sign-in and browser console warnings

**`No auth provider found matching the given token`:** Convex rejected the Firebase token before account linking or role checks. Check the deployment used by the affected website, not just whichever deployment `npx convex dev` most recently configured:

1. Compare the public `NEXT_PUBLIC_CONVEX_URL` built into that website with the URL in the Convex dashboard. A Vercel production deployment and a developer's `npx convex dev` deployment are often different. `.env.local` affects the local web app, not an already deployed Vercel build.
2. In that exact Convex deployment's Settings → Environment Variables, set `FIREBASE_PROJECT_ID` to the exact Firebase project ID. It must match the `NEXT_PUBLIC_FIREBASE_PROJECT_ID` used when building the frontend, and must not be an API key, Firebase app ID, Google OAuth client ID, URL, or Firebase project number.
3. Deploy `convex/auth.config.ts` to that same deployment. For local development restart `npx convex dev` after setting the variable and wait for a successful deployment. For Vercel production, deploy using a production deploy key targeting that deployment (see above) and redeploy the site after changing its public variables. Do not point a preview deploy key at production by accident.
4. Sign out and sign in again. If the error persists, check the Firebase project and the exact deployment used by the client. Convex requires an exact issuer and audience match; the expected issuer is `https://securetoken.google.com/<project-id>` and the expected audience is `<project-id>`. Never paste a raw ID token or deploy key into chat or a third-party decoder. No code can configure an inaccessible deployment automatically.

**`Cross-Origin-Opener-Policy ... window.closed`:** Pulso sets `Cross-Origin-Opener-Policy: same-origin-allow-popups` to allow the Firebase sign-in popup relationship. After deployment, inspect the response headers of the site and check whether Vercel, a proxy, or another rule overrides it. Google pages or browser extensions may still produce popup-policy warnings; a warning alone does not prove login failed. The relaxed policy means the application is not cross-origin isolated.

**Unrecognized `Permissions-Policy` features:** Those warnings come from a response header encountered by the browser, potentially from Google or another third-party response. Pulso does not set those directives. Check the Network tab to identify the response before changing any header; third-party headers cannot be fixed in this repository. They do not establish why Convex rejected a Firebase token.

**WebSocket reconnect:** Convex reconnects automatically after transient network interruptions. A successful reconnect is not the same as successful authentication; resolve the provider mismatch separately. If reconnects are continuous, check network access and the deployment status.

**Generic “University account required / We could not confirm your sign-in”:** A frontend from PR #7 can show this when the connected deployment returns the older `accounts.status` response without a diagnostic reason. The same message can also mean the backend returned `missing_identity`; it does not establish which case occurred. Verify the site’s `NEXT_PUBLIC_CONVEX_URL`, deploy the current `accounts.status` and auth configuration to that exact deployment, then sign out and sign in. If using Vercel, the production deployment is not automatically updated by `npx convex dev` on a developer machine. Do not delete or modify the accounts table to troubleshoot.

## Instructor Classroom classification (in progress)

Instructors can connect their own Google Classroom account, browse published coursework, and confirm or change an AI-suggested category. Configure `GEMINI_API_KEY` as a sensitive **server-side Vercel** variable; the optional `GEMINI_CLASSIFICATION_MODEL` defaults to `gemini-3.5-flash-lite`. The selected Google Cloud project must allow the model and have usage limits configured. Task titles and descriptions are sent to Gemini on opening a course. If the key/model is unavailable or the model response is invalid, no suggestion is shown and the instructor chooses manually. Do not put the key in `NEXT_PUBLIC_` variables or logs.

Enable the teacher read-only Classroom coursework scope on the OAuth consent screen. Teachers must authorize their own accounts; a previous student-only grant may need reconnecting. Review decisions are saved per instructor. Confirmed, dated, course-wide published work can appear in Classroom-derived views after successful sync; it is not imported into legacy manual section assessments. Verified course-offering/roster mapping, individually assigned work scoring, and combined cross-subject section workload are not implemented. Material is a separate Classroom resource and is not included in coursework review. There has been no live end-to-end test of teacher OAuth or Gemini classification.

## Classroom subject sync and admin heatmap

Set the same long random `CLASSROOM_SYNC_SECRET` (at least 32 characters) as a sensitive server-side Vercel variable and a Convex environment variable for the matching deployment. Never expose it as a `NEXT_PUBLIC_` variable. Deploy the Convex schema/functions and web app together. Each instructor and student must connect and refresh Classroom; snapshots are not automatically refreshed in the background. Disconnect deletes that account's snapshots. Instructors may need to reconnect to grant teacher scopes. Subject listings include active, provisioned and archived courses; only active courses contribute to the workload. Pagination fetches up to 100 pages and fails explicitly if more are needed.

The instructor course heatmap and admin Home instructor-based summary count only current published, confirmed, course-wide work with due dates, weighted quiz 1, activity 2, exam 3; targeted assignments, materials, missing/unconfirmed work and grade weights are excluded. Groups with fewer than five active connected student snapshots are suppressed. The combined student count includes only connected active students and suppresses counts under five. Snapshots may be stale or incomplete; they are not a roster, and do not support verified course attendance. They refresh only on an owner's request, not automatically. The old manually entered section data is preserved but no longer drives the admin heatmap or student dashboards. A live Classroom end-to-end test is still required.

Instructor Crunch Weeks refreshes the connected teacher's courses on opening and shows one row per Classroom course, using Classroom's course name and optional section label. Admin Crunch Weeks uses connected student Classroom memberships and dated-item counts, grouped by matching section labels; see Student-based admin Crunch Weeks below. Admin Subjects and Home still use instructor snapshots. Co-teachers of the same Classroom course share one admin row. Different Classroom courses are not merged based on matching section text: that label is not a verified shared cohort identifier. The instructor heatmap counts confirmed course-wide work with due dates per class, not a combined cross-subject section workload. Instructor Home, Sections and Crunch Weeks now use Classroom classes; legacy manually entered section records remain in the database but are not displayed there.

### Empty dashboards troubleshooting

A Classroom tab can display live Google data even when saving the shared snapshot fails. Check the sync notice in the instructor Classroom tab or the admin sync-status panel. If syncing fails, check that `CLASSROOM_SYNC_SECRET` is at least 32 characters and identical in the **server-side Vercel environment for the site** and **Convex environment for the exact deployment referenced by that site**. Generate a unique random value locally (for example, `openssl rand -hex 32`), set it privately in both dashboards, and never paste it into chat or expose it in a `NEXT_PUBLIC_` variable. Deploy the current Convex schema/functions to that deployment and redeploy Vercel after changing its environment, then have each instructor and student refresh Classroom. A valid-looking secret in Convex alone does not prove that Vercel matches.

Published student work remains visible in personal views even when not confirmed; it is labelled unscored. Shared workload requires an instructor to refresh and confirm each category, a due date, and course-wide assignment. Admin cells also require at least five connected students who refreshed the same class. A dash or unavailable score is not zero. Check the selected week and course refresh status. There has been no production end-to-end validation.

### AI suggestions troubleshooting

Instructor Classroom review requests Gemini from the web server. Set `GEMINI_API_KEY` as a sensitive Vercel variable for the environment serving the app, then redeploy Vercel. The API key needs access to the Gemini API and the configured model; `GEMINI_CLASSIFICATION_MODEL` is optional and defaults to `gemini-3.5-flash-lite`. A bad key, disabled API, unavailable model, insufficient project access, quota limits, or a network failure can prevent suggestions. The review screen now displays a safe error category and a retry button; it never exposes the key or Google response. AI is advisory, and an instructor can always choose and confirm manually. Do not share the key in chat. The service has not been tested end-to-end with live Google credentials in this environment.

### Student-based admin Crunch Weeks

Admin Crunch Weeks groups connected students' active Classroom classes by their teacher-provided section label. Matching labels are only an approximation and may combine unrelated cohorts; missing section labels remain separate by Classroom course ID. Values are averages of each connected student's visible, published, dated Classroom items per week, including individually assigned and unconfirmed items. They are not category-confirmed workload scores or unique shared deadlines. The server stores only per-course weekly counts, not assignment titles or IDs, for this view. Groups under five connected students are suppressed; groups with any unavailable or older unsynced coursework are marked unavailable. Refreshes are per student, and this is not a complete roster.

Deploy the updated Convex schema/functions and web app together; each student must refresh Classroom after deployment to send section labels and counts. No instructor connection or AI classification is required for this view. Google Classroom authorization and sync must still be configured. Classroom data is stale until the student refreshes; live verification is still required.

### Automatic student deadline breakdown

Student Home, Timeline and Crunch Weeks show published dated coursework from the student's own Classroom connection immediately; neither instructor registration nor category confirmation is needed. To produce a personal estimated score, the server can send each assignment's title (up to 200 characters) and Classroom work type to Gemini; the student view does not send descriptions. These AI categories are estimates, not confirmed classifications, and do not update shared scores. If Gemini is not configured, a classification fails, or a course fails to load, the deadlines still appear but the affected estimated score is unavailable rather than zero. Configure `GEMINI_API_KEY` on Vercel as described above. Assignments without due dates remain in Classroom and are not placed in a week. AI requests are made for dated work in the displayed four-week range after loading or refreshing Classroom, and as students navigate to new weeks; monitor provider quota and cost. Authenticated connected accounts are limited to 60 recommendation batches per minute, up to five items per batch. Deploy the Convex schema and functions along with the web app. Live end-to-end validation remains necessary.

### Refreshing connected students from Admin Crunch Weeks

Admin Crunch Weeks now refreshes active students' existing, individually authorized Classroom connections in small batches when opened, and offers a retry button. This uses the existing encrypted student refresh tokens on the web server; only the student's weekly counts are stored, never assignment titles or IDs for the admin view. A student can disconnect Classroom to remove their connection and snapshots. The admin-only server bridge requires both an authorized admin session and `CLASSROOM_SYNC_SECRET`; it never returns tokens or student-specific data to the browser. Failed connections are marked unavailable rather than represented as zero, and the five-student threshold is unchanged. This cannot show a student who has never connected. This workflow has not yet been tested against live Google credentials.

### Gemini diagnostic messages

The Gemini request runs in the **web app server**, not Convex. Set `GEMINI_API_KEY` on the exact Vercel project and environment serving the site, and redeploy after changes. The optional `GEMINI_CLASSIFICATION_MODEL` is a bare model ID (default `gemini-3.5-flash-lite`), not a URL or `models/` path. Enable the Gemini API for the key's Google project and check key restrictions and access to that model. The instructor view distinguishes an invalid key, access denied, missing model/endpoint, rejected request, quota and temporary failure where the provider's response permits it; generic rejections cannot identify a precise root cause. Do not paste a key or raw provider response into chat. Manual categorization remains available. A successful live request must still be verified with the real deployment.

Google restricts Gemini 2.5 access for some projects; a 404 can indicate the configured model is not available to that project, not necessarily an invalid API key. If `GEMINI_CLASSIFICATION_MODEL` is explicitly set to the older model, change it to an available model such as `gemini-3.5-flash-lite` (or remove the override to use the default), then redeploy the web app. Project access, region, quota and provider changes can still affect availability.
